## Base Configuration

```
Base URL: /api
Content-Type: application/json
Timeout: 10000ms (10 seconds)
```

The frontend Axios client (`src/services/client.ts`) is configured with:
- `baseURL` from `NEXT_PUBLIC_API_URL` (default: `http://localhost:3001/api`)
- `timeout` of 10000ms
- Default `Content-Type: application/json` header

## Authentication & Token Handling

All authenticated endpoints require a `Bearer` token in the `Authorization` header:

```
Authorization: Bearer <access_token>
```

### Token Storage (Client-Side)

The frontend stores tokens in `localStorage` under the following keys:
- `accessToken` — JWT access token
- `refreshToken` — JWT refresh token

### Automatic 401 Handling

The frontend Axios interceptor automatically:
1. Attaches the `accessToken` from `localStorage` to every request
2. On `401` response: removes both `accessToken` and `refreshToken` from `localStorage`
3. Rejects the promise with `error.response.data` or a fallback `{ message: 'Network error', statusCode: 500 }`

## Posts Endpoints

### GET /posts

Get paginated list of posts with optional sorting and filtering.

**Query Parameters:**

> **Important**: The frontend sends filters as a nested object via Axios `params` serialization. Axios serializes nested objects using bracket notation by default (e.g., `filters[category]=ai`). The backend should parse these accordingly, OR alternatively accept flat query parameters and the frontend can be adjusted.

| Parameter           | Type   | Default  | Description                                  |
|---------------------|--------|----------|----------------------------------------------|
| page                | number | 1        | Page number                                  |
| limit               | number | 12       | Items per page                               |
| sort                | string | "recent" | Sort order: `"recent"`, `"popular"`, `"liked"` |
| filters[category]   | string | —        | Filter by category slug                      |
| filters[query]      | string | —        | Search query (matches title, preview, tags)  |

**Response (200):** [PaginatedResponse](#paginatedresponset)\<[Post](#post)\>

```json
{
  "data": [Post],
  "total": 100,
  "page": 1,
  "limit": 12,
  "totalPages": 9
}
```

**Frontend Reference:** `src/services/api/postsApi.ts` > `getPosts()`, consumed by `src/hooks/usePosts.ts` > `usePosts()`

**Used on pages:**
- `/blog` — Blog listing page (limit: 12)
- `/` — Home page (indirectly, via trending/latest/recommended)

### POST /posts

Create a new post.

**Headers:** Requires authentication.

**Request Body:** [PostCreate](#postcreate) object.

```json
{
  "title": "string",
  "preview": "string",
  "content": "string (markdown)",
  "coverImage": "string (URL, optional — frontend sends default if empty)",
  "category": "string (Category slug)",
  "tags": ["string"]
}
```

**Response (201):** The created [Post](#post) object (including generated `id`, `slug`, `readingTime`, timestamps, and `author` from the authenticated user).

**Errors:**

- `401` Unauthorized
- `400` Validation error

**Notes:**
- The backend should auto-generate the `slug` from the title
- The backend should compute `readingTime` from content length (~200 words per minute)
- `author` should be populated from the authenticated user

**Frontend Reference:** `src/services/api/postsApi.ts` > `createPost(data)`, consumed by `src/hooks/usePosts.ts` > `useCreatePost()`

**Used on pages:** `/blog/new` (New post editor)

## Activity Endpoints

The frontend records user activities via the backend API. The backend is responsible for XP calculation, level progression, streak tracking, and badge awarding.

### POST /activity

Record a user activity event. The backend should calculate and award XP based on the activity type.

**Headers:** Requires authentication.

**Request Body:**

```json
{
  "type": "read_post | like_post | like_idea | daily_visit",
  "entityId": "string"
}
```

**Response (200):**

```json
{
  "xp": 10,
  "totalXp": 130,
  "level": 2
}
```

**Notes:**
- The backend should handle deduplication (e.g., reading the same post twice should not award XP twice)
- The `entityId` is used for deduplication (e.g., post ID for read_post, `daily-YYYY-MM-DD` for daily_visit)
- The backend should update the user's XP, level, streak, and badges accordingly

**Frontend Reference:** `src/lib/api/activity.ts` > `recordActivity()`

**Used by:** `src/components/features/DailyVisitChecker.tsx` (records daily_visit on app mount)

## Pagination Contract

### PaginatedResponse\<T\>

All paginated endpoints return this envelope:

```typescript
interface PaginatedResponse<T> {
  data: T[];             // Array of items for the current page
  total: number;         // Total number of items matching the query
  page: number;          // Current page number (1-indexed)
  limit: number;         // Items per page
  totalPages: number;    // Total number of pages (ceil(total / limit))
}
```

### PaginationParams

Frontend query parameter structure:

```typescript
interface PaginationParams {
  page?: number;         // Default: 1
  limit?: number;        // Default: 12 (except /todo which uses 10)
}
```

### Default Limits by Page

| Page       | Endpoint    | Default Limit |
|------------|-------------|---------------|

| `/search`  | GET /search | 12            |
| `/todo`    | GET /todo   | 10            |

## Error Response Format

The frontend expects error responses to conform to this structure:

```typescript
interface ApiError {
  message: string;       // Human-readable error message
  statusCode: number;    // HTTP status code
  error?: string;        // Optional error type/code
}
```

The frontend Axios interceptor extracts `error.response.data` and rejects with it. If no response data is available, it falls back to:

```json
{ "message": "Network error", "statusCode": 500 }
```

## CORS Configuration

The backend must allow CORS from the frontend origin (default `http://localhost:3000`).

Required CORS settings:
- **Allowed Origins:** `http://localhost:3000` (or configured `NEXT_PUBLIC_APP_URL`)
- **Allowed Methods:** `GET`, `POST`, `PATCH`, `DELETE`, `OPTIONS`
- **Allowed Headers:** `Content-Type`, `Authorization`
- **Credentials:** `true` (for cookie-based features if added later)

## JWT Configuration

- Access tokens should expire in **15 minutes**
- Refresh tokens should expire in **7 days**
- Tokens should be signed with a secure secret
- The frontend currently does **not** implement automatic token refresh — on 401, it simply clears tokens and the user must re-authenticate

| Hook                  | Query Key                     |

## Gamification (Backend-Handled)

The XP/gamification system must be handled **entirely by the backend**. The frontend only displays values returned by the API (via `GET /auth/profile` and `POST /activity`).

### Gamification Events

The backend must implement XP rewards for the following activities:

| Action         | Suggested XP | Trigger                        |
|----------------|-------------|--------------------------------|
| `read_post`    | 10          | Viewing a blog post            |
| `like_post`    | 5           | Liking a blog post             |
| `like_idea`    | 3           | Liking a todo idea             |
| `daily_visit`  | 15          | First visit each calendar day  |

### Badges

Suggested badge definitions (backend should award and return in user profile):

| Badge ID      | Name       | Condition                |
|---------------|------------|--------------------------|
| `first-read`  | First Read | Read 1 article           |
| `5-articles`  | Bookworm   | Read 5 articles          |
| `10-likes`    | Generous   | Give 10 likes            |
| `streak-3`    | On Fire    | 3-day visit streak       |
| `streak-7`    | Dedicated  | 7-day visit streak       |
| `first-post`  | Author     | Create 1 post            |

### Deduplication

The backend must handle XP deduplication — XP is only awarded once per action+entity combination. For example, viewing the same post twice should only grant XP on the first view.

### Frontend Gamification Display

The frontend stores gamification data from the API in a Zustand store (`gamificationStore`) for display purposes only. It does NOT calculate XP, levels, or badges — it only renders what the API returns.

Gamification data sources:
- `GET /auth/profile` returns `xp`, `level`, `badges`, `streak` on the User object
- `POST /activity` returns `xp` earned and updated `totalXp`, `level`
